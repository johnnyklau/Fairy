A corrupted model file crashed the whole app instead of degrading gracefully

ffi onnx data-integrity
Symptom
On a completely fresh reinstall, the eye rendered fine — then the whole app vanished the instant it was clicked.
Looked like
The reinstall itself, or the auto-update feature that had just been added and tested that same day.
Actually was
One model file (vector_estimator.int8.onnx) silently truncated on disk since weeks earlier — undetected the whole time because every voice test since then happened to hit a warm disk cache and never actually reload it.
Fix
is_model_ready() now checks each file's size against a manifest recorded at download time, not just that the file exists.

Both obvious suspects were ruled out fast: an A/B build from before the reinstall and before the auto-update feature existed crashed identically, and the crash reproduced on an already-settled, minutes-old process — not just right at launch. That left the model itself. A directory listing showed it immediately: six of the seven model files shared one timestamp from the original download; the seventh was dated weeks later and ~2MB smaller than a freshly redownloaded copy turned out to be. Something had overwritten just that one file, incompletely, long ago.

The reason nobody had seen this coming: synthesize() checks an in-memory and on-disk cache before ever touching the model, keyed by a hash of the exact text. Every earlier "voice works" confirmation — including several earlier the same day — had been a cache hit, serving bytes synthesized long before the corruption happened. The corrupted file only mattered the moment something asked for a line that had never been cached, which turned out not to happen for weeks.

When it finally did, OfflineTts::create tried to parse the truncated file and ONNX Runtime threw a C++ exception. That exception tried to unwind across the Rust/FFI boundary, and Rust's runtime did exactly what it's designed to do with a foreign exception it can't safely catch: it hard-aborted the entire process, printing fatal runtime error: Rust cannot catch foreign exceptions, aborting. No amount of catch_unwind on the Rust side would have helped — this is the same fundamental limit as the eager-load crash further up this page, just reached through a different door.

Lesson. A cache doesn't just speed up the common path — it can quietly stop testing the uncommon one. "It works" only means the path actually taken works; a bug can sit fully formed on a colder path for as long as nothing happens to need it.

The installed app crashed on every launch once voice was enabled

ffi startup onnx
Symptom
The installed release build died on launch every time, but only once voice was turned on — dev/debug builds never showed it.
Looked like
A bad install or a corrupted binary; the fault offset in the Windows crash log shifted between builds, which pointed away from one fixed line of code.
Actually was
The TTS model being loaded eagerly at startup, crossing into sherpa-onnx's C++ engine while WebView2/window/COM initialization was still settling.
Fix
Removed the eager-load call from .setup() entirely — the model now only loads lazily, on the first real synthesis request.

An earlier attempt at a fix wrapped the eager-load call in std::panic::catch_unwind, on the theory that whatever was going wrong was a Rust panic that just needed catching. It wasn't enough — the crash came back with a different fault offset on a later build, which ruled that theory out directly. The reason: a panic that originates on the C++ side of an FFI boundary doesn't unwind into catchable Rust code at all; it triggers a hard process abort (Windows exception 0xC0000409) before control ever returns to the Rust frame wrapping the call. catch_unwind can only intercept panics that unwind through Rust — this one never did.

Confirmed by direct A/B testing on the same previously-crashing installed binary: with the eager-load call present, it crashed on every launch; with it removed, it launched cleanly and the first reminder still synthesized correctly a little later, right when it was actually needed.

Lesson. A safety net that catches most bugs can create false confidence about the ones it can't reach. FFI boundaries are exactly where that gap shows up — the calling language's usual guarantees stop applying the moment execution crosses into the other side.

Reminder audio was silently blocked by the browser's own security policy

webview2 csp audio
Symptom
Clicking the eye showed a popup that vanished almost instantly, with no audio — as if voice were completely broken.
Looked like
A backend problem: IPC not reaching Rust, or synthesis failing silently.
Actually was
Chromium's Content-Security-Policy blocking a blob: audio load, three components downstream of everything that was actually suspected.
Fix
One line in tauri.conf.json: media-src 'self' blob:.

Tracing the click command by command showed it did reach Rust, the model did synthesize real audio, and a correct clip duration did come back over the IPC bridge — every layer that looked suspicious was actually working exactly as designed. The failure was one step further downstream, inside WebView2 itself.

Playing audio in the frontend works by wrapping the returned bytes in a blob: URL and handing it to an <audio> element — but Fairy's CSP only listed default-src 'self', with no explicit rule for media. Chromium doesn't let blob: audio quietly inherit that default; it needs its own permission. So the browser itself refused to load the clip, audio.play() rejected immediately, and Fairy's own error handling (built to fail quietly rather than crash the UI) dismissed the popup right on schedule. Nothing in Rust, IPC, or the voice pipeline was ever at fault.

Lesson. In a two-runtime app — native backend plus an embedded browser engine — "it doesn't work" can fail at the Rust layer, the IPC bridge, or inside the browser engine itself, and those look identical from the outside. Naming which of the three you're looking at is most of the debugging work.
