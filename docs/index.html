Fairy, Explained

Fairy is a small Windows app: a glowing eye that sits in the corner of your screen, occasionally tells you to drink water or take a break, and — if you switch voice on — says so out loud in a voice modeled on a robotic AI companion. This walks through how it's built, one layer at a time.

01

The elevator pitch

Fairy is a desktop wellness companion — a small, always-on-top window shaped like a single eye, docked in a corner of the screen. On a timer, or when you've been idle too long, it pops up a short line of text ("drink some water, master") and, if voice is enabled, speaks it. The character is modeled on Fairy, the robotic AI companion from the game Zenless Zone Zero — so the voice isn't meant to sound clean or assistant-like. Raw synthesized speech gets deliberately pitched up, distorted, and bit-crushed until it reads as something mechanical talking to you, not a polite virtual assistant.

Under the hood, that single visible eye is the tip of two quite different pieces of software glued together and shipped as one Windows installer: a small, safety-focused systems language doing the thinking, and a full web browser engine doing the drawing. The rest of this tour is about how those two pieces cooperate, and what each of Fairy's features costs to build once you look past the eye itself.

02

Two processes in a trenchcoat

Fairy is built with Tauri. The idea: instead of writing native Windows UI code (verbose, and a different world from web development), let the UI be ordinary HTML/CSS/TypeScript, and let the operating system's already-installed browser engine render it. On Windows that engine is WebView2 — the same rendering engine as Microsoft Edge, just running invisibly inside Fairy's window instead of inside a browser tab.

The other half is a native fairy.exe written in Rust. It owns everything that isn't drawing: reading settings from disk, deciding when a reminder should fire, running the text-to-speech engine, talking to the Windows tray icon. The two halves genuinely don't share memory or a language — they're bridged entirely through message-passing, covered next.

Why not Electron? Electron (Slack, VS Code, Discord) takes the same "web UI, native backend" idea but ships its own copy of Chromium and Node.js inside every installer — reliable, but every app pays the weight of a full browser download. Tauri instead rents the browser engine Windows already has installed, so Fairy's installer is a few megabytes, not a few hundred.
03

How the two sides talk

Because the UI and the logic are different processes in different languages, they can't just call each other's functions directly. Tauri gives them exactly two ways to communicate, and Fairy uses both:

Commands are the frontend asking the backend for something and waiting for an answer — the closest analogy is a very fast, purely local RPC call. A Rust function marked #[tauri::command] becomes callable from TypeScript as invoke("command_name", args), which returns a Promise. get_flavor_lines, synthesize_flavor_line, and report_eye_bounds are all commands like this.

Events run the other way: the backend pushes information whenever it decides something changed, without the frontend having asked. Fairy emits one called state_changed every time anything about its state changes — a reminder firing, a setting being updated — and the frontend just has a standing subscription (listen) that reacts.

04

The illusion of a floating eye

Fairy's window has no title bar, no border, and no taskbar icon, floats above every other window, and is only 460×220 pixels — configured directly in Tauri's window settings, not something built by hand. That part's straightforward. The interesting trick is what happens when nothing is supposed to be there: Fairy needs to let you click through its window onto whatever's underneath, everywhere except the small circle where the eye actually is.

Windows offers exactly one lever for this — a window can be made entirely "click-through," meaning the OS delivers no mouse input to it at all, full stop. That's a problem: if the window can't receive mouse events, it also can't notice the mouse arriving to know when to turn itself back on. Fairy's fix is a background Rust task that sidesteps the window entirely and asks Windows directly, 60 times a second, "where is the cursor right now?" — then compares that against the eye's actual screen position (which the frontend reports any time layout changes) and flips the window's click-through flag on or off accordingly.

05

What Fairy is thinking

Rather than the frontend keeping its own copy of "is a reminder showing, what does it say, which corner is the window in," all of that lives in one Rust struct — CompanionState — and the UI's only real job is: whenever a fresh copy of that state arrives, throw away any assumptions and redraw to match it exactly. This is the same single-source-of-truth pattern frameworks like React popularize — Fairy just hand-rolls it in a few dozen lines rather than pulling in a framework, since the UI itself is small (one eye, one popup).

Settings are a separate, longer-lived layer: whether voice is on, how often to remind you to drink water, which screen corner to dock in. Those get written to an actual JSON file on disk the moment you change them (via Tauri's storage plugin), so they survive a restart — Fairy reads that file once at launch and otherwise treats it as the settings UI's problem to keep in sync.

06

The scheduler

A background loop wakes up periodically and asks a short list of questions: has it been long enough since the last water reminder? Is it the configured time of day for a workout reminder? Has the mouse been untouched long enough to earn an idle "bark"? This loop runs on Rust's async runtime (Tokio), the same underlying idea as JavaScript's event loop, just on the Rust side — nothing about "wait, then check again" blocks anything else Fairy is doing.

When a reminder does fire, the scheduler doesn't just show text — it decides how long the popup should stay up. With voice off, that's a fixed, generous reading time; with voice on, it's the actual measured length of the synthesized clip, so the popup never vanishes mid-sentence or lingers awkwardly after the audio's done. Either way, the result is written into CompanionState, and — per section 05 — the UI update happens automatically from there.

07

Teaching the fairy to talk

This is the most involved part of the codebase. The voice comes from Supertonic, a small neural text-to-speech model distributed in ONNX format, run through a Rust crate called sherpa-onnx that wraps a C++ inference engine. That last part matters: crossing from Rust into C++ code and back is called FFI, and Rust's normal safety net (which turns most bugs into a clean, catchable error) doesn't reach across that boundary — a crash originating on the C++ side can bring the whole process down instantly, which is exactly what an earlier version of Fairy hit: loading the model too early, before Windows had finished setting the app up, corrupted enough state to crash on nearly every launch (see Field Notes for the full writeup).

The model itself is ~145MB, so it isn't bundled in the installer — Fairy downloads it once, the first time you switch voice on, and checks the download's SHA-256 hash against a value GitHub itself computed at upload time, so a corrupted or interfered-with download is caught before it's ever loaded.

Then it gets run through a robot

Raw model output sounds clean and a little flat — a human voice, not the robotic companion the character is modeled on. So every clip is run through a chain of hand-written audio effects tuned to recreate that synthesized, mechanical vocal character before anyone hears it: pitched up a few semitones, pushed through a distortion waveshaper, bit-crushed, given a wobble (vibrato), and finished with a reverb built from short delay lines — the same "comb and allpass filter" building blocks used in classic studio reverb units — before a final safety pass makes sure nothing clips.

The finished clip is hand-encoded as a plain 16-bit WAV file, base64-encoded, and sent to the frontend over the same command/response channel from section 03 — from there, playing it is the browser's job, which is its own separate point of failure (see Field Notes for a case where that's exactly where a bug turned out to live).

08

From source to installer

Building Fairy is really two independent builds glued together by Tauri's own build step. The TypeScript/HTML/CSS side is compiled and bundled by Vite — the same category of tool used by most modern web frontends. The Rust side is compiled by Cargo, Rust's standard build tool, into a single release-mode fairy.exe. Tauri's build command runs both, in order, then embeds the finished frontend files directly inside the executable — Fairy never reaches onto disk or the network at runtime just to find its own UI.

FrontendVite compiles TS/HTML/CSS → static files
EmbedThose files get baked into the Rust binary
CompileCargo builds release-mode fairy.exe
PackageWiX → .msi, NSIS → setup.exe

Two separate Windows packaging tools then wrap that one exe into two installer formats side by side — an .msi (via WiX, the format enterprise deployment tools expect) and a friendlier _setup.exe (via NSIS) — so people can use whichever their situation calls for.

Both halves carry their own safety nets, run automatically on every change: the Rust side has 56 unit tests plus clippy (Rust's linter, opinionated enough to catch real bugs, not just style) and rustfmt; the TypeScript side has its own test suite (Vitest), eslint, prettier, and the TypeScript compiler's own type-checker (tsc) run in check-only mode.
